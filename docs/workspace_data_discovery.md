# Workspace data discovery

## Outcome

The workspace-wide preflight found **no qualifying field-sales CSV**. The audit inspected **135 CSV files and 4 XLSX files** and compared their headers with the 17 expected commercial fields:

`Distributor`, `Customer`, `City`, `Country`, `Latitude`, `Longitude`, `Channel`, `Sub-channel`, `Product Name`, `Product Class`, `Quantity`, `Price`, `Sales`, `Month`, `Year`, `Sales Manager`, and `Sales Team`.

No inspected file matched more than one of those fields. Consequently, no available file could support the required field-representative × product × territory × month analysis. The benchmark therefore uses the explicit fallback dataset generated by the repository. Results from this run are synthetic/demo evidence and must not be presented as analysis of the team's original commercial dataset.

## Notable rejected candidates

The audit did find pharmaceutical files, but subject-matter proximity was not treated as schema fitness:

| Candidate | What it contains | Why it was rejected |
|---|---|---|
| `pharma-launch-analytics-dashboard/.../financial_table.csv` | 366 rows × 50 columns of annual corporate financials for 79 companies, covering 2021–2026 | Company-level financial reporting has no representative, customer, transaction, product-sale, territory, manager, or activity grain. |
| `pipeline_raw.csv` | 271,151 rows × 4 columns of drug-development records: company, drug, condition, and development phase | It has no sales, quantity, price, customer, geography, field-force organization, activity, target, or incentive fields. |

These examples are recorded to make the decision auditable without copying unrelated datasets or exposing full workspace file dumps.

## Automated repository discovery

At run time, `data_loader.py` performs a narrower, reproducible discovery pass over the configured `data/raw` directory and `paths.search_roots` in `configs/config.yaml`.

The loader:

1. recursively examines CSV headers;
2. normalizes punctuation and case and checks known column aliases;
3. scores core evidence (`customer`, `product_name`, `sales`, `quantity`, and `month`) and all expected fields;
4. requires at least three core matches and seven total matches before a candidate is plausible;
5. selects deterministically by schema score, file size, and path when more than one candidate qualifies; and
6. excludes `data/synthetic`, `data/processed`, `artifacts`, and `.venv`, preventing a later run from ingesting its own generated outputs.

An explicitly supplied input path takes precedence and is still schema-adapted and validated. The automated loader currently ingests CSV; the broader preflight also checked the four workbook candidates so that a plausible source was not missed merely because it used XLSX.

## Fallback used for this benchmark

With no qualifying source, the seeded fallback generator creates `data/synthetic/fallback_pharma_sales.csv` with **9,000 transaction-like rows** over **18 months beginning January 2024**. It provides the expected commercial shape across distributors, customers, cities, countries, coordinates, channels, products, quantities, prices, sales, managers, and teams. Relationships such as `sales ≈ quantity × price`, location opportunity, product demand, seasonality, and trend are built into generation.

This table is deliberately source-like, but it is **not original source data**. The later representative mapping, activity/target/incentive enrichment, engineered features, and evaluation labels are separate layers; see `data_dictionary.md`.

## Audit evidence

Every run writes provenance and data-quality evidence:

- `data/synthetic/provenance.json`: selected source or fallback, reason, discovery audit, schema mapping, row count, and seed;
- `artifacts/reports/data_quality_report.json`: shape, duplicates, missingness, date coverage, and categorical coverage;
- `artifacts/reports/data_quality_report.md`: human-readable summary; and
- `artifacts/metrics/data_quality_columns.csv`: per-column type, null count, cardinality, descriptive statistics, and most-common category where applicable.

When a real dataset becomes available, place it in `data/raw/` or pass it explicitly to the pipeline. Confirm the provenance report says `source_type: provided_csv` and `fallback_used: false` before treating results as source-based.
